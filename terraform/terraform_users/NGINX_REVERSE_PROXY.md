# NGINX Reverse Proxy Implementation

## Overview

This implementation uses NGINX as a reverse proxy within each EC2 instance to route traffic from the Application Load Balancer (ALB) to the appropriate Docker containers.

## Architecture

```
Internet
    ↓
Application Load Balancer (Port 80)
    ↓
EC2 Instance (Port 80)
    ↓
NGINX Reverse Proxy (Port 80)
    ↓
    ├─→ API Gateway (localhost:3000)
    │   ├─→ Auth Services (localhost:3006-3008)
    │   ├─→ File Services (localhost:3011-3015)
    │   └─→ Users Services (via direct routing)
    │
    ├─→ users-create (localhost:3001) [Direct]
    ├─→ users-delete (localhost:3002) [Direct]
    ├─→ users-list (localhost:3003) [Direct]
    ├─→ users-search (localhost:3004) [Direct]
    └─→ users-update (localhost:3005) [Direct]
```

## Traffic Flow

### 1. Client Request
```
Client → ALB (Port 80) → EC2 Instance (Port 80)
```

### 2. NGINX Routing
NGINX receives the request on port 80 and routes based on URL path:

#### Direct Service Routing (Users Services)
- `POST /api/users/create` → `http://127.0.0.1:3001/api/users`
- `DELETE /api/users/:id` → `http://127.0.0.1:3002/api/users/:id`
- `GET /api/users` → `http://127.0.0.1:3003/api/users`
- `GET /api/users/search` → `http://127.0.0.1:3004/api/users/search`
- `PUT /api/users/:id` → `http://127.0.0.1:3005/api/users/:id`

#### API Gateway Routing
- `GET /api/health` → `http://127.0.0.1:3000/api/health`
- `GET /api/logs` → `http://127.0.0.1:3000/api/logs`
- `POST /api/auth/login` → `http://127.0.0.1:3000/api/auth/login`
- `GET /api/auth/me` → `http://127.0.0.1:3000/api/auth/me`
- `GET /api/auth/roles` → `http://127.0.0.1:3000/api/auth/roles`
- `POST /api/files/init-student` → `http://127.0.0.1:3000/api/files/init-student`
- `GET /api/files/list` → `http://127.0.0.1:3000/api/files/list`
- All other `/api/users/*` routes → `http://127.0.0.1:3000/api/users/*`

### 3. Container Response
```
Container → NGINX → ALB → Client
```

## Security

### Container Isolation
- All Docker containers listen **only on localhost** (127.0.0.1)
- Containers are not directly accessible from outside the instance
- Only NGINX (port 80) is exposed to the ALB

### Security Groups
- ALB Security Group: Allows inbound port 80 from 0.0.0.0/0
- EC2 Security Group: Allows inbound port 80 only from ALB Security Group
- EC2 Security Group: Allows inbound port 22 for SSH (optional, for debugging)

## Configuration Files

### NGINX Configuration
- **Location**: `/etc/nginx/conf.d/api-gateway.conf`
- **Generated by**: `user-data-template.sh`
- **Features**:
  - Upstream definitions for all services
  - Path-based routing
  - Proper proxy headers
  - Error handling
  - Timeout configuration

### User Data Script
- **File**: `user-data-template.sh`
- **Responsibilities**:
  1. Install Docker and NGINX
  2. Configure Docker login
  3. Create `.env` file with environment variables
  4. Generate NGINX configuration
  5. Deploy all Docker containers (listening on localhost)
  6. Start NGINX
  7. Verify connectivity

## Container Deployment

### Services Deployed
1. **users-create** (Port 3001)
2. **users-delete** (Port 3002)
3. **users-list** (Port 3003)
4. **users-search** (Port 3004)
5. **users-update** (Port 3005)
6. **api-gateway** (Port 3000)

### Container Configuration
- All containers use `--restart always` for automatic restart
- Containers bind to `127.0.0.1:PORT` (localhost only)
- Environment variables loaded from `/home/ubuntu/.env`

## Environment Variables

The `.env` file contains:
- Database configuration
- Service URLs (all pointing to localhost)
- JWT secret
- Docker registry credentials

**Important**: All service URLs point to `localhost` since NGINX routes internally.

## Startup Sequence

1. **Docker Installation** → Docker service starts
2. **NGINX Installation** → NGINX service installed (not started yet)
3. **Docker Login** → Authenticate with Docker Hub/Registry
4. **Environment Setup** → Create `.env` file
5. **NGINX Configuration** → Generate `/etc/nginx/conf.d/api-gateway.conf`
6. **Container Deployment** → Pull and run all containers
7. **Container Health Check** → Wait 10 seconds for containers to initialize
8. **NGINX Start** → Start NGINX service
9. **Verification** → Test NGINX connectivity to containers

## Health Checks

### ALB Health Check
- **Path**: `/` (root path)
- **Protocol**: HTTP
- **Port**: 80
- **Interval**: 60 seconds
- **Timeout**: 10 seconds
- **Healthy Threshold**: 2
- **Unhealthy Threshold**: 5
- **Matcher**: 200, 404

### Container Health
- Containers are checked via NGINX
- If a container is down, NGINX returns 502/503/504
- ALB marks instance as unhealthy if health checks fail

## Auto Scaling Group Compatibility

### Instance Refresh
- **Strategy**: Rolling
- **Min Healthy Percentage**: 50%
- **Instance Warmup**: 180 seconds
- **Triggers**: Tag changes

When instance refresh is triggered:
1. New instances launch with updated Launch Template
2. User data script runs automatically
3. NGINX and containers deploy
4. New instances register with ALB
5. Old instances drain and terminate

### Health Check Type
- **Type**: EC2 (not ELB)
- **Reason**: Prevents unnecessary instance replacement
- **Checks**: Only verifies instance is running, not application health

## Troubleshooting

### Check NGINX Status
```bash
sudo systemctl status nginx
sudo nginx -t  # Test configuration
```

### Check Container Status
```bash
docker ps
docker logs <container-name>
```

### Test NGINX Routing
```bash
# From within the instance
curl http://localhost/api/health
curl http://localhost/api/users
```

### View NGINX Logs
```bash
sudo tail -f /var/log/nginx/access.log
sudo tail -f /var/log/nginx/error.log
```

### View User Data Logs
```bash
sudo tail -f /var/log/user_data.log
```

## Benefits

1. **Single Entry Point**: ALB only needs to point to port 80
2. **Path-Based Routing**: Clean URL structure
3. **Security**: Containers not directly exposed
4. **Flexibility**: Easy to add/remove services
5. **Load Balancing**: ALB distributes across instances
6. **Health Monitoring**: NGINX provides additional health check layer
7. **Auto Scaling**: Compatible with ASG and instance refresh

## Limitations

1. **Single Instance**: If NGINX fails, entire instance is down
2. **No SSL/TLS**: HTTP only (can be added with Let's Encrypt)
3. **Manual Configuration**: NGINX config is static (can be templated)

## Future Enhancements

1. **SSL/TLS**: Add HTTPS support with Let's Encrypt
2. **Dynamic Configuration**: Use Consul/etcd for service discovery
3. **Metrics**: Add Prometheus/Grafana for monitoring
4. **Logging**: Centralized logging with ELK stack
5. **Rate Limiting**: Add NGINX rate limiting rules
